# Production ownership and release runbook

Current-state evidence must be rechecked before each release. Repository ownership transfer and privatisation are deferred for this pilot; they are not release gates. The live production safeguards are a protected `main` branch, a green `verify` check, automatic Vercel production deployment from `main`, and a documented rollback path.

This runbook separates repository-controlled safeguards from company-admin work. No step below authorizes changing the live GitHub, Vercel, Supabase, Microsoft 365, or DNS environment without an approved change ticket.

## Repository-enforced release contract

- `.github/workflows/ci.yml` runs on every pull request and push to `main` with Node 22, `npm ci`, a high/critical production-runtime dependency-audit gate, a visible development-dependency audit report, lint, typecheck, unit/security tests, and a production build.
- Vercel Git integration deploys `main` automatically after a green protected merge. `.github/workflows/production-rollback.yml` is manual recovery only: it restores a named last-known-good Vercel artifact and never promotes normal releases.
- `package-lock.json` is authoritative. Release jobs use `npm ci`, never a floating install.
- Production database changes are forward migrations. Migrations must be applied and verified before the dependent application merge; never merge code that requires an unapplied destructive migration.

## Release procedure

1. Confirm the pull request is green on `verify`, all required review policy is met, and any required migration is already applied.
2. Record the current READY Vercel production deployment URL and commit SHA.
3. Merge the pull request to protected `main`; Vercel automatically deploys that merge.
4. Verify `/api/cron/email/run` authentication, `/admin/system-health`, sign-in tenant/allowlist rejection, one approved booking workflow, and logs for new errors.
5. If smoke checks fail, run **Production rollback** with the recorded READY deployment URL and record the result.

## Application rollback

List deployments with `vercel ls`, inspect the candidate with `vercel inspect DEPLOYMENT_URL`, and restore the last known-good artifact with `vercel rollback DEPLOYMENT_URL` (or `vercel promote LAST_GOOD_URL`). The Vercel release owner records old/new deployment IDs and post-rollback smoke results. Database rollback is independent: never deploy older application code if it is incompatible with already-applied forward migrations.

## Secret handling

Secrets belong in the company vault and provider environment stores. Evidence must show names, scope, rotation timestamp, and owner - never values. If a secret is found in Git history, immediately revoke/rotate it first, remove it with an approved history-rewrite procedure, invalidate caches/forks where possible, and attach provider revocation evidence.
